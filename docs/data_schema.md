# Client Request Normalizer — схема данных v1.0

**Проект:** нормализация клиентских запросов о компьютерной технике и IT-услугах.  
**Язык входных запросов и документации:** русский.  
**Формат ответа:** JSON с английскими именами полей и кодами категорий; текстовые значения — на русском языке или в оригинальном написании бренда.

## 1. Цель

Преобразовать свободно сформулированное обращение клиента в структурированную запись для последующей обработки в CRM, каталоге товаров или системе заявок. Модель **не** определяет реальные цены и остатки, не выполняет заказы и не диагностирует оборудование.

В первой версии поддерживаются запросы цены, заказы IT-услуг и вопросы о наличии компьютерных товаров. Прочие обращения получают категорию `unknown`.

## 2. Контракт ответа

Ответ модели — **ровно один JSON-объект**, без пояснений, Markdown и дополнительных ключей. Все семь полей обязательны.

```json
{
  "intent": "price_request",
  "item_type": "service",
  "item": "установка Windows",
  "brand": null,
  "quantity": 2,
  "location": null,
  "deadline": null
}
```

### Поля

| Поле | Тип | Правило заполнения |
|---|---|---|
| `intent` | строка | `price_request`, `service_order`, `availability_request` или `unknown` |
| `item_type` | строка или `null` | `product` — товар; `service` — услуга; `null` — определить нельзя |
| `item` | строка или `null` | Краткое нормализованное наименование товара или услуги; `null`, если объект не определён |
| `brand` | строка или `null` | Только явно названный производитель/бренд; сохраняем исходное написание |
| `quantity` | целое число или `null` | Положительное целое число, только если количество однозначно указано |
| `location` | строка или `null` | Явно указанное место выполнения работ/доставки; без догадок |
| `deadline` | строка или `null` | Явно указанный срок в исходной формулировке; без вычисления календарной даты |

### Значения `intent`

- `price_request` — клиент спрашивает стоимость товара или услуги, в том числе в формулировке «во сколько обойдётся».
- `service_order` — клиент явно просит выполнить IT-услугу: установить, настроить, подключить, обслужить и т. п.
- `availability_request` — клиент уточняет наличие товара.
- `unknown` — запрос не относится к поддерживаемым сценариям либо намерение нельзя установить уверенно.

**Приоритет при пересечении:** если клиент одновременно упоминает заказ и явно спрашивает цену, выбираем `price_request`. Если одновременно просит услугу и спрашивает наличие товара, но основной цели нет, выбираем `unknown` (в v1 один запрос — одно намерение).

## 3. Правила нормализации

1. Извлекать только сведения, содержащиеся в запросе. Не выдумывать цены, остатки, совместимость, бренды, количества и даты.
2. Если поле отсутствует или неоднозначно, возвращать `null`, а не пустую строку или «не указано».
3. Относительные сроки («до пятницы», «на следующей неделе») оставлять текстом; без опорной даты их нельзя переводить в конкретные даты.
4. Нормализовать общепринятые названия: «винда» → «Windows», «эсэсди» → «SSD», если значение очевидно из контекста. Не добавлять неуказанные характеристики.
5. `quantity` — только целое положительное число: «два ноутбука» → `2`; «несколько ноутбуков» → `null`.
6. Если запрос содержит обращение за технической консультацией, а не коммерческий запрос («Компьютер не включается, что делать?»), ставить `intent: "unknown"`. Другие поля заполнять лишь при наличии явно выраженных данных; для первого тестового примера допустимы `null` во всех остальных полях.
7. В версии v1 не поддерживаем несколько независимых товарных позиций в одном запросе: `intent: "unknown"` при невозможности выделить одну основную позицию.
8. Любое изменение полей или правил требует новой версии схемы и обновления обучающих и тестовых примеров.

## 4. Эталонные примеры

### Запрос стоимости

**Вход:** «Сколько стоит установить Windows на два ноутбука?»

```json
{"intent":"price_request","item_type":"service","item":"установка Windows","brand":null,"quantity":2,"location":null,"deadline":null}
```

### Заказ услуги

**Вход:** «Нужно настроить Wi-Fi в офисе на следующей неделе»

```json
{"intent":"service_order","item_type":"service","item":"настройка Wi-Fi","brand":null,"quantity":null,"location":"офис","deadline":"на следующей неделе"}
```

### Наличие товара

**Вход:** «Есть три SSD Samsung по 1 ТБ?»

```json
{"intent":"availability_request","item_type":"product","item":"SSD 1 ТБ","brand":"Samsung","quantity":3,"location":null,"deadline":null}
```

### Неподдерживаемое обращение

**Вход:** «У меня компьютер не включается, что делать?»

```json
{"intent":"unknown","item_type":null,"item":null,"brand":null,"quantity":null,"location":null,"deadline":null}
```

## 5. Формат датасета

Используем JSON Lines (`.jsonl`): одна обучающая запись на строку, UTF-8.

```json
{"instruction":"Есть три SSD Samsung по 1 ТБ?","output":{"intent":"availability_request","item_type":"product","item":"SSD 1 ТБ","brand":"Samsung","quantity":3,"location":null,"deadline":null}}
```

- `instruction` — исходное обращение на русском языке.
- `output` — эталонный JSON-объект по схеме v1.
- Перед обучением скрипт сериализует `output` в JSON-строку единообразно.
- Нельзя допускать попадания одних и тех же сценариев с минимальными перефразировками в обучение и тестирование.

## 6. Разделение данных

Стартовый план — **120 записей**:

| Набор | Количество | Назначение |
|---|---:|---|
| `train.jsonl` | 90 | Обучение LoRA |
| `validation.jsonl` | 15 | Подбор параметров и проверка во время разработки |
| `test.jsonl` | 15 | Финальная независимая оценка |

Разделяем примеры по семействам сценариев, а не случайно по близким перефразировкам. Тестовый набор не используем для настройки модели.

## 7. Оценка качества

Сравниваем базовую **Qwen2.5-0.5B-Instruct** и модель с LoRA-адаптером на одинаковых тестовых запросах и с одинаковой инструкцией.

- **JSON parse rate** — доля ответов, которые удалось разобрать как JSON.
- **Schema-valid rate** — доля ответов, содержащих ровно семь полей с допустимыми типами и значениями.
- **Intent accuracy** — точность определения намерения.
- **Per-field accuracy** — точность каждого поля, включая правильное использование `null`.
- **Exact match** — доля ответов, у которых совпадают все поля после разбора JSON (порядок ключей не учитывается).

Результаты эксперимента фиксируем в `results/` и документируем в README. Улучшение после LoRA не предполагаем заранее — его необходимо измерить.

## 8. Границы версии и развитие

**Для ДЗ:** одна позиция в запросе, три коммерческих намерения + `unknown`, семь полей, локальная модель и измеримое сравнение до/после LoRA.

**Для портфолио:** несколько позиций, расширенная схема характеристик товаров, API, валидация ответа, интеграция с каталогом и обработка уточняющих вопросов. Эти возможности не входят в v1.
